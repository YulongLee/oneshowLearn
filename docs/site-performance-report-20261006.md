# OneShowLearn 全站性能检查报告

检查日期：2026 年 10 月 6 日。对象：当前线上 OneShowLearn 及对应源代码。

结论：网站有明确的性能优化空间，优先处理前端加载体积、大图片、字体依赖和重复请求。目前的低负载采样没有显示需要立即升级服务器；但这不等于已经通过高并发或真实用户体验验收。建议保留现有设计与商业逻辑，分阶段提速，而不是重新设计或重构整个产品。

本轮只进行代码检查、现有构建产物分析、匿名 HTTPS 读取和服务器只读诊断。未修改业务代码、配置、价格、用户资料或数据库内容，未触发支付、AI、短信和邮件服务，未部署或上传 Git。

## 检查范围与限制

检查覆盖官网、登录和共享框架、工作台、课程阅读、项目、AI 导师、资源、社区、笔记、收藏、成果、设置及收银台相关代码；线上采样覆盖首页、登录和工作台入口，以及公开价格、课程目录、学习入口、项目、资源和官网配置接口。共享入口的加载问题会影响多个页面。

需要明确区分：

- **线上确认**：实际文件大小、压缩和缓存响应、HTTP 协议、少量请求耗时、服务器瞬时资源状态。
- **代码确认**：静态导入、重复请求、轮询、全量状态和先全量处理再分页等实现方式。
- **风险推断**：这些实现可能影响弱网、低配置设备及未来数据增长，但尚未量化每项实际影响。

浏览器采集工具两次超时，本轮没有取得有效的浏览器性能轨迹、Lighthouse 评分或 LCP、INP、CLS 实测值。也没有取得真实用户监控数据，未进行登录用户完整操作性能测试、地区弱网测试、视频并发测试或压力测试。报告不能作为全站性能达标或并发容量证明。

### 服务器采样

OneShowLearn 服务运行中，服务内存约 63 MB。整机约 3.7 GB 内存，可用约 2.8 GB；磁盘使用率约 35%；1、5、15 分钟负载约为 0.07、0.11、0.09。数据库文件约 717 KB，当前数据规模较小。

这些是低负载时的一次快照，只支持“当时没有明显资源紧张”的判断，不支持承诺同时在线或并发播放人数。

## 优化项目与优先级

P1 表示建议第一批处理；P2 表示随后优化或在数据增长前完成；P3 表示需要专项测量后决定。

| 优先级 | 问题 | 证据与影响 | 建议 |
| --- | --- | --- | --- |
| P1 | 大多数学习功能共用一个较大入口 | 主 JS 约 1.14 MB；App 静态导入课程、项目、AI、资源、个人工作区等。官网和登录页也引用同一入口 | 按公共页和学习功能拆分；重编辑、收银台和非当前路由功能按需加载 |
| P1 | 主要宣传图片体积较大 | 首页 1.71 MB，购买页人物 1.24 MB、横幅 1.46 MB | 在清晰度验收后输出 WebP 或 AVIF 和不同宽度版本；下方图片懒加载 |
| P1 | 关键图片在执行页面代码后才被发现 | 入口 HTML 只有空根节点；首页主图虽然有高优先级，但由 React 渲染 | 提前发现真实首屏图片；必要时对公开官网预渲染，不对私人页面做公共缓存 |
| P1 | 全站 CSS 依赖 Google Fonts 外部导入 | 全局样式顶部存在远程 `@import`，包含多个字重 | 优先使用系统字体，或在授权允许时自托管必要字体；保留中文与品牌视觉 |
| P1 | 缺少可见的持续性能采集 | 所检查代码未发现 Web Vitals 上报或页面性能预算 | 建立隐私安全的性能基线，按页面和设备区分，不记录私人正文或票据 |
| P2 | 全站 CSS 集中加载 | 主 CSS 约 571 KB，多个路由样式随静态导入进入入口 | 跟随路由拆分样式，测量未使用覆盖率，再清理历史规则 |
| P2 | 路由切换重复读取公开价格和目录 | SidebarCourseOffer 的 effect 依赖 route；每次切换读价格和学习入口。购买页另有同类读取 | 共享进行中的请求、短时复用并后台刷新；价格与权限变更必须正确失效 |
| P2 | 无变化时仍周期读取 AI 状态和历史 | 能力接口每 30 秒；已有对话每 15 秒、待回复时每 1.5 秒 | 页面不可见且无待处理任务时降频；恢复可见时刷新，保留失败恢复 |
| P2 | 项目分页前先处理全部项目 | 后台先读取所有发布项目并逐个求摘要，最后才 slice；摘要含多次查询 | 先在数据库筛选分页，再批量读取关联数据；排序统计必须保持准确 |
| P2 | 私人工作区和笔记存在全量读写路径 | 工作区 GET 含完整 state；个人笔记等随状态整体提交。笔记页逐页读取全部课时笔记以保证完整搜索 | 逐步分离摘要、正文和单项操作；服务端搜索和按需正文读取，保留完整搜索、版本和草稿保护 |
| P2 | AI 检索每次重复构造文本块 | tutor-retrieval 每次枚举可读材料并分词、分块、排序，处理上限仍较大 | 缓存发布版本的文本块或使用文本索引；每次仍重新核验账号和课时权限 |
| P2 | 网络传输和静态缓存仍可细化 | 当前 HTTP/1.1；带指纹 JS 和未带指纹图片共用 7 天缓存 | 验证启用 HTTP/2；仅对带指纹文件长缓存和 immutable，保留 HTML 重验证 |
| P3 | 播放时多个组件状态持续更新 | timeupdate 同时更新播放器、阅读区时间和进度状态 | 用 React 性能轨迹定位后隔离高频更新，不能破坏跳转、同步课件和退出保存 |
| P3 | 私有视频通过应用转发 OSS 数据流 | materials 路由校验权限后使用 pipeline 转发，已有 Range 支持 | 长视频与并发增加时测量带宽；评估支持权限撤销的私有分发或 CDN 方案 |

“按需加载”要结合真实依赖图拆分；不能只把文件分成多个 chunk，却依然让官网自动加载所有块。二维码库目前通过 CourseCheckout 静态导入，是候选拆分对象，但本轮未取得该库在最终包中的独立占比。

首屏图片的发现时间与传输大小是两件事。只给 React 内的图片加高优先级，不能消除等待 JavaScript 执行的时间。[Google 首屏图片优化说明](https://web.dev/articles/optimize-lcp)支持先测量下载发现和渲染延迟，再决定预加载或预渲染。

对于内容指纹文件，长期缓存与 immutable 可以减少不必要的重验证；未带指纹且可能同名替换的宣传图片不能直接照搬一年缓存。[MDN 缓存说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control)

| 笔记和收藏 | 页面代码拆分，避免重复读目录 | 搜索和正文分离，保留精确来源链接和未保存草稿 |

| 购买和收银台 | 大图与非首屏横幅优化，收银台按需加载 | 支付查询有待处理状态时仍必须及时核验 |

## 已有合理实现与必须保留的边界

已有的性能措施包括：JS 和 CSS 压缩、静态缓存、持久化学习框架、后台管理页面和富文本编辑器分块、首页部分下方图片懒加载、视频 metadata 预加载与 Range 分段读取，以及 SQLite WAL 模式。课程进度和笔记保存虽然有定时器，但会检查变化，不是每次定时都无条件写数据库。

当前主要不是“完全没有优化”，而是随着多次功能和视觉开发，公共入口和共享样式累积，需要系统整理。

以下边界不能为提速而削弱：

- 不能公共缓存用户资料、私有笔记、订单、会员群二维码、带私人权限的接口或下载票据。
- 价格展示可以短时复用，但下单金额必须由服务端权威配置决定；到账后开通权益仍以签名与金额核验为准。
- 不能移除笔记、成果和工作区的版本冲突保护，或为了少一次请求而覆盖另一窗口的新内容。
- 路由拆分不能卸载尚在播放的视频、清空未发送问题或丢失编辑草稿。
- 检索缓存必须正确处理取消发布、更新、退款或到期等权限变化；不能直接复用另一用户的授权结果。
- 视频分发不应简单把 OSS 私有桶改为公共桶，也不能用长期公开地址替代现有权限校验。

## 建议实施顺序

### 第一阶段 优化首次进入体验

先补可复现的桌面和手机基线，再处理首页与购买页大图、外部字体、公共与学习页面代码拆分、路由 CSS。保持页面视觉验收，防止图片清晰度或字体布局退化。这是本轮证据最明确、最值得优先投入的一组工作。

### 第二阶段 减少重复工作

统一公开价格与目录的读取和失效规则，优化后台标签页轮询，验证 HTTP/2 和带指纹资源缓存。涉及 Nginx 的调整应单独检查对同机其他站点的影响；不能把本报告当作生产配置修改授权。

### 第三阶段 为正式内容和增长准备

优化项目真实分页、批量查询、笔记摘要与全文搜索，分离大的私人状态读写，优化 AI 文本块构造。数据库索引应先通过查询计划和隔离大数据样本验证，不因出现 SQLite 就直接迁移数据库。

### 第四阶段 按真实视频流量决定分发方案

使用正式长视频和隔离测试账号验证首播、拖动、清晰度、移动网络及并发带宽，然后决定是否引入私有 CDN 或更多码率。当前不能从演示视频和低负载快照推断正式视频容量，也不建议先盲目购买更高配置服务器。

## 优化后的验收标准

建议建立以下验收目标，而不是先承诺某个评分或提升百分比：

- 记录同一设备和网络下的冷缓存、热缓存及路由切换基线，优化前后可重复比较。
- 官网和登录实际网络中不加载无关项目、AI、笔记编辑器或收银台功能代码；进入对应页面时才加载必要块。
- 首屏图片使用匹配显示尺寸的资源，画质经人工确认；下方大图不竞争首屏下载。
- 无变化的连续路由切换不重复执行相同公开数据请求；账户切换和配置更新能立即正确失效。
- 手机、桌面分别跟踪 LCP、INP、CLS。正式目标参考真实访问第 75 百分位：LCP 不超过 2.5 秒、INP 不超过 200 ms、CLS 不超过 0.1；这些是建议目标，不是本轮实测成绩。[Google Web Vitals 标准](https://web.dev/articles/vitals)
- 增长型接口在隔离的数百项目、上限笔记及较长对话样本下验证响应、内存和查询计划；不要在生产制造测试记录或做高强度压测。
- 所有性能改动后重新验证登录、支付状态与历史金额、课程权限、私有资料、收藏来源、草稿、冲突和离开保存保护。
- 补充真实用户样本后再决定扩容；任何预计收益都以改后测量为准。
